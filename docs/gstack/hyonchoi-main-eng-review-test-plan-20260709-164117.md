# Test Plan
Generated by /autoplan (eng-review phase)
Branch: main

## Affected Pages/Routes
- None (backend-only: outbound HTTP header selection for vLLM/SGLang providers)

## Key Interactions to Verify
- vllm/sglang provider configured with AuthType::ApiKey sends `Authorization: Bearer <key>`, not `x-api-key`
- Every other provider type (anthropic, openrouter, z.ai, minimax, kimi-coding, nvidia-nim) still sends `x-api-key` under AuthType::ApiKey (regression guard)
- vllm/sglang provider configured with AuthType::Passthrough still sends the caller's passthrough token as Bearer, not the configured api_key
- vllm/sglang provider configured with OAuth (if a supported combination) still sends Bearer

## Edge Cases
- custom_headers containing an "Authorization" or "x-api-key" entry alongside the new header_style — verify no duplicate header is sent (or document as known limitation)
- count_tokens code path for vllm/sglang, if reachable — same header assertion as send_message/stream

## Critical Paths
- End-to-end: a vllm-configured provider with a real (or mock) vLLM server rejecting x-api-key and accepting Bearer — confirms the fix resolves the actual reported bug, not just the header name in isolation
