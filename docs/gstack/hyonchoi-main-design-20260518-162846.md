## Problem Statement

The background Copilot token refresh fix (25ceb60) prevents idle Copilot providers from
silently expiring their 30-minute bearer tokens. The same idle-expiry problem affects any
OAuth-based provider (Gemini, OpenAI-compatible, Anthropic-compatible) that isn't in the
active fallback chain and receives no requests. These providers have no background refresh —
they only refresh on-demand, which means a provider idle for >1 hour comes back with an
expired token and a silent failure.

## What Makes This Cool

One background task loop handles every OAuth provider in the system. No provider ever
silently expires while idle. The threshold logic adapts to any token TTL instead of
hardcoding a 5-minute check. Adding a new OAuth provider in the future gets background
refresh for free by adding one match arm.

## Constraints

- Copilot refresh (`fetch_copilot_token`) is a GitHub-internal API: exchanges GitHub PAT →
  Copilot bearer. It is NOT a standard OAuth 2.0 refresh_token grant and cannot share the
  `OAuthClient::refresh_token()` path.
- Standard OAuth providers (Gemini, OpenAI, Anthropic-compatible) already have
  `OAuthClient::refresh_token()` wired for on-demand refresh in their respective providers.
- The background loop must use the same threshold approach as the Copilot fix: check
  `remaining_time < POLL_INTERVAL + buffer`, not the hardcoded `needs_refresh()` 5-minute
  check.
- Scope: extend the existing single tokio background loop only. No new per-provider tasks.

## Premises

1. Copilot refresh stays separate from standard OAuth refresh — different protocols,
   different call paths. No unification possible at the function level.
2. The threshold check CAN be unified: one `needs_background_refresh(token, poll_interval)`
   function replaces both `copilot_token_needs_background_refresh()` and `needs_refresh()`.
3. The background loop dispatches via `match provider_config.provider_type.as_str()`.
4. OAuthConfig selection per provider_type:
   - `"gemini"` → `OAuthConfig::gemini()` (confirmed exists in `src/auth/oauth.rs:107`)
   - `"openai"` → `OAuthConfig::openai_codex()` (confirmed exists in `src/auth/oauth.rs:84`)
   - `"anthropic"` → `OAuthConfig::anthropic()` (confirmed exists in `src/auth/oauth.rs:55`).
     Note: `provider_type` value is `"anthropic"` (not `"anthropic_compatible"`) — the struct
     is `AnthropicCompatibleProvider` but the registry match uses `"anthropic"`. Sub-types
     like `"nvidia-nim"`, `"z.ai"` that also use `AnthropicCompatibleProvider` could
     theoretically use OAuth too, but are out of scope for this change.
5. Scope: exactly these three provider_type strings. No abstraction layer.
6. `OAuthClient::refresh_token(&provider_id)` internally calls `token_store.save()` on
   success. Standard OAuth branches do NOT need manual save. Copilot branch continues
   manual save via `bg_token_store.save()` (since it calls `fetch_copilot_token` directly).
7. `ProviderConfig.oauth_provider: Option<String>` exists on the struct
   (`src/providers/mod.rs:98`). When `None`, the fallback is
   `provider_config.name.clone()` (per `registry.rs:71` — uses `unwrap_or_else`).
   The background loop reads `provider_config.oauth_provider.clone().unwrap_or_else(|| provider_config.name.clone())`
   for the TokenStore lookup key.
8. The background loop must guard on `auth_type == OAuth` before attempting refresh.
   Some provider types (e.g., Gemini) support both API key and OAuth auth. A provider
   configured with `auth_type = ApiKey` has no token in TokenStore — attempting OAuth
   refresh on it would log spurious warnings every 20 minutes.
8. Background poll interval: 20 minutes (same as Copilot). Standard OAuth access tokens
   are typically 1-hour TTL, so 20-minute poll + buffer keeps them comfortably fresh.
   `REFRESH_BUFFER` = 5 minutes (matching existing Copilot logic where
   `COPILOT_REFRESH_THRESHOLD_SECS` ≈ poll_interval + 5 min).

## Approaches Considered

### Approach A: Minimal Extend
Add `else if` branches in the existing Copilot loop. Keep Copilot-specific threshold.
Others use `needs_refresh()`. Quick, but leaves two different threshold functions and
uses the wrong 5-min TTL for non-Copilot tokens.

### Approach B: Unified Threshold + Per-Provider Dispatch (chosen)
Extract a generic `needs_background_refresh(token, poll_interval)` function. Background
loop dispatches via `match` on `provider_type`. One threshold function for all providers.
Copilot refresh function stays (`fetch_copilot_token`); others use `OAuthClient::refresh_token()`.

### Approach C: Per-Provider tokio Task
Spawn a separate background task per OAuth provider. True isolation, but adds task
proliferation and shutdown coordination complexity for what is currently a 20-line loop.

## Recommended Approach

**Approach B.** The unified threshold is a one-function extraction (~10 lines) that makes
every future provider automatically correct. The match dispatch is readable and the total
diff is small. No abstraction overhead; Copilot path is untouched beyond the threshold
function rename.

## Open Questions

1. **Repeated refresh failures**: What happens when `refresh_token` fails for a standard
   OAuth provider on every poll cycle? The Copilot branch logs a warning and moves on. For
   standard OAuth, if the refresh_token itself has been revoked (Google revokes after 6 months
   of inactivity), the loop will warn every 20 minutes forever. Should there be a circuit
   breaker or exponential backoff after N consecutive failures? Out of scope for this change,
   but worth a follow-up TODO.

## Success Criteria

- All three non-Copilot OAuth provider types have background refresh running after server start.
- `cargo test` passes with no regressions.
- `info!("Background refresh: renewed ...")` log lines appear for each provider type in
  a server run where all three are configured.
- `cargo clippy` clean.

## Distribution Plan

Existing deployment pipeline covers this — server-side change, no new binary, no config
format change.

## Next Steps

1. **Add `needs_background_refresh(token: &OAuthToken, poll_interval: Duration) -> bool`**
   to `src/server/mod.rs`. Logic: `token.expires_at - now() < poll_interval + REFRESH_BUFFER`
   where `REFRESH_BUFFER = 5 min`. This replaces `copilot_token_needs_background_refresh()`.
2. **Update the Copilot branch** in the background loop to call the new generic function.
3. **Extend the background loop** with match arms for `"gemini" | "openai" | "anthropic"`:
   - Read `provider_config.oauth_provider.or(&provider_config.name)` as the provider_id
   - Select `OAuthConfig` per provider_type: `"gemini"` → `OAuthConfig::gemini()`,
     `"openai"` → `OAuthConfig::openai_codex()`, `"anthropic"` → `OAuthConfig::anthropic()`
   - Create `OAuthClient::new(config, token_store.clone())` (cheap, done per iteration;
     `OAuthClient` is stateless beyond config + token_store)
   - Call `oauth_client.refresh_token(&provider_id).await` — this internally saves the
     refreshed token to TokenStore. No manual save needed.
   - Log success/failure the same way as the Copilot branch
4. **Write tests** — unit test for `needs_background_refresh()`, plus extract a
   `refresh_provider_if_needed(provider_config, token_store) -> Result<()>` function
   that contains the match dispatch and threshold check. Unit tests call this function
   directly with mock tokens. The tokio interval loop becomes a thin wrapper that
   iterates providers and calls this function.
5. **Run `cargo clippy` + `cargo test`** before shipping.

## What I noticed about how you think

- You asked "can we unify Copilot's refresh into the general path?" before agreeing to
  premises — not "sure, whatever." That's the right question to ask: always check if the
  protocol assumptions hold before accepting a design.
- You picked the approach that handles future cases correctly (unified threshold) over the
  one that ships fastest. That's taste, not just expedience.
- You kept scope tight throughout: "just the remaining 3 provider types," no abstraction
  layer unless it earns its keep.
