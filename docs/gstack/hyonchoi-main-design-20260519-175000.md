## Problem Statement

The Copilot provider (`src/providers/copilot.rs`) sends incomplete headers to the GitHub
Copilot API. The API tracks session state via headers that our proxy omits entirely:
`Openai-Organization`, `X-Request-Id`, `VScode-SessionId`, `VScode-MachineId`,
`X-GitHub-Api-Version`, `X-Interaction-Type`. After 3–6 normal responses the server
returns 400 Bad Request with no body — strongly correlated with the server losing track
of an orphaned session.

A secondary bug: on 401, the retry path calls `get_valid_copilot_token()` again, which
re-checks `needs_refresh()`. If the token is between the 5-minute gate and actual expiry,
the same stale token is returned and the retry fails again.

~~A third gap (TODOS.md P2): background OAuth refresh exists only for Copilot; Gemini,
OpenAI, and Anthropic-compatible providers silently expire when idle.~~ **Already shipped**
in `src/server/mod.rs` via `needs_background_refresh()` and `refresh_provider_if_needed()`.

## What Makes This Cool

Copilot API calls carry a header fingerprint matching VSCode — stable session/machine IDs,
per-request UUID correlation. No more silent 400 cascade. The 401 race condition is
eliminated with a force-refresh path. Transient network errors get one quiet retry.

## Premises (all agreed 2026-05-19, revised per plan-eng-review)

1. The 400 errors are caused by missing session/tracking headers that the Copilot API
   requires for multi-turn request correlation (primarily VScode-SessionId and
   VScode-MachineId; X-Interaction-Id is a secondary analytics header — deferred).
2. `X-Request-Id` must be a fresh UUID per API call. `VScode-SessionId` and
   `VScode-MachineId` must be stable UUIDs generated once at provider startup
   (not per-request). The `uuid` crate is the right tool; add it to Cargo.toml.
3. On 401, force-expire the cached token by passing `force: true` to
   `get_valid_copilot_token()`, bypassing the `needs_refresh()` gate and guaranteeing
   a fresh token fetch.
4. ~~Background OAuth refresh generalization~~ — **Already shipped**. Change 3 removed.
5. The full connectionState.ts 8-state machine is out of scope. A single retry on
   network-level errors (timeout/reset/DNS, not 4xx/5xx) is the right scope.
6. X-Interaction-Id is **deferred** from this PR. Per-call diverges from the reference
   (which scopes it per-conversation). Omit it until the session/machine ID fix is
   validated empirically; then add it as a per-conversation UUID in a follow-up.

## Architecture

### Change 1: Missing Copilot Headers (`src/providers/copilot.rs`)

**Headers to add** (from reference networking.ts + chatMLFetcher.ts):

```rust
// Static — added to COPILOT_HEADERS const
"Openai-Organization": "github-copilot"
"X-GitHub-Api-Version": "2025-05-01"
"X-Interaction-Type": "conversation"

// Per-provider-instance — generated once at CopilotProvider::new()
"VScode-SessionId": <uuid_v4_at_startup>
"VScode-MachineId": <uuid_v4_at_startup>

// Per-request — generated fresh in apply_copilot_headers()
"X-Request-Id": <uuid_v4_per_call>

// DEFERRED: X-Interaction-Id — will be added as per-conversation UUID
// in a follow-up after the session/machine ID fix is validated.
```

**CopilotProvider struct** gains two fields:
```rust
pub struct CopilotProvider {
    // ... existing fields ...
    session_id: String, // VScode-SessionId — stable for provider lifetime
    machine_id: String, // VScode-MachineId — stable for provider lifetime
}
```

`CopilotProvider::new()` generates both with `uuid::Uuid::new_v4().to_string()`.

**Header-builder helper** (D1 — eliminates 4-way duplication):
```rust
fn apply_copilot_headers(
    builder: reqwest::RequestBuilder,
    session_id: &str,
    machine_id: &str,
) -> reqwest::RequestBuilder {
    let mut builder = builder;
    for (key, value) in COPILOT_HEADERS {
        builder = builder.header(*key, *value);
    }
    builder
        .header("VScode-SessionId", session_id)
        .header("VScode-MachineId", machine_id)
        .header("X-Request-Id", uuid::Uuid::new_v4().to_string())
}
```

Called from all 4 request sites (stream initial, stream 401 retry, non-stream initial,
non-stream 401 retry). Per-request UUIDs generated inside this helper.

**COPILOT_HEADERS const** — add 3 static entries (now 8 total):
```rust
const COPILOT_HEADERS: &[(&str, &str)] = &[
    ("Editor-Version", "vscode/1.107.0"),
    ("Editor-Plugin-Version", "copilot-chat/0.35.0"),
    ("Copilot-Integration-Id", "vscode-chat"),
    ("Openai-Intent", "conversation-edits"),
    ("X-Initiator", "user"),
    ("Openai-Organization", "github-copilot"),       // NEW
    ("X-GitHub-Api-Version", "2025-05-01"),           // NEW
    ("X-Interaction-Type", "conversation"),            // NEW
];
```

**Cargo.toml** — add `uuid = { version = "1", features = ["v4"] }`.

### Change 2: Force-Invalidate on 401 (`src/providers/copilot.rs` + `src/auth/github_copilot.rs`)

Current 401 retry:
```rust
// 401 → call get_valid_copilot_token() again — may return SAME token if < 5 min old
```

Fixed: add `force` parameter to `get_valid_copilot_token()`:
```rust
async fn get_valid_copilot_token(&self, force: bool) -> Result<String, ProviderError> {
    // Fast path: check without lock
    if let Some(token) = token_store.get(&self.name) {
        if !force && !token.needs_refresh() {
            return Ok(token.access_token.clone());
        }
    }
    // ... rest unchanged, but the double-check also uses force:
    if force || token.needs_refresh() {
        // fetch fresh token
    }
}
```

401 retry call: `self.get_valid_copilot_token(true).await?` in both streaming
and non-streaming 401 retry blocks.

### Change 3: Network Error Single Retry (`src/providers/copilot.rs`)

Scope: connection-level errors only (reqwest timeout, connection reset, DNS failure).
NOT 4xx/5xx. NOT mid-stream failures (once headers are accepted, we're committed).

**X-Request-Id on retry:** The retry path MUST regenerate a fresh X-Request-Id. After
`try_clone()`, do NOT reuse the cloned builder directly — call `apply_copilot_headers()`
again on the cloned builder to generate a new UUID. This avoids potential deduplication
by GitHub's API and ensures the retry log line carries a distinct, traceable request ID.

Implementation uses `try_clone()` (D2) before `.send()`:
```rust
let cloned = req_builder.try_clone();
let response_result = req_builder.send().await;
let response = match response_result {
    Err(e) if e.is_connect() || e.is_timeout() => {
        if let Some(retry_builder) = cloned {
            tracing::info!(
                session_id = %self.session_id,
                error = ?e.kind(),
                attempt = 1,
                "Copilot network retry"
            );
            tokio::time::sleep(std::time::Duration::from_millis(500)).await;
            // Regenerate X-Request-Id for the retry attempt
            let retry_builder = apply_copilot_headers(retry_builder, &self.session_id, &self.machine_id);
            retry_builder.send().await.map_err(ProviderError::HttpError)?
        } else {
            return Err(ProviderError::HttpError(e));
        }
    }
    other => other.map_err(ProviderError::HttpError)?,
};
```

Note: Copilot chat completions endpoints are idempotent for reads. Non-streaming
retry is safe. Streaming retry only applies before the stream opens.

## Observability — Structured Log Lines

All three recovery paths emit structured `tracing` log lines. These are the **canonical
log signatures** developers and contributors should use for verification and debugging:

```rust
// 1. Session init (in CopilotProvider::new())
tracing::info!(
    session_id = %session_id,
    machine_id = %machine_id,
    "Copilot session established"
);

// 2. Network retry (in send path)
tracing::info!(
    session_id = %self.session_id,
    error = ?e.kind(),
    attempt = 1,
    "Copilot network retry"
);

// 3. 401 force-refresh (in 401 retry path)
tracing::info!(
    session_id = %self.session_id,
    "Copilot 401: force-refreshing token"
);
```

**Verification**: enable logging with `RUST_LOG=ccm=info cargo run` and look for:
- `Copilot session established` — confirms the fix is active on startup
- `Copilot network retry` — confirms the single-retry path fired
- `Copilot 401: force-refreshing token` — confirms the 401 force-invalidate fired

### Manual tests

1. **400 regression** — Run a long Claude Code session (>10 turns) through the
   Copilot provider. Verify no 400 errors.
   **Verification**: Check ccm logs for `Copilot session established [session_id=...]`.
   Presence of this log line confirms the fix is active. Absence means the binary
   is not updated — confirm version with `ccm --version`.

2. **401 force-invalidation** — Trigger a 401 by expiring the cached Copilot token:
   - Stop ccm
   - Open `~/.claude-code-mux/tokens.json` (or the token store file documented in
     `docs/OAUTH_TESTING.md`) and set the Copilot token's `expires_at` to a past
     timestamp (or delete the token entry entirely)
   - Restart ccm
   - Make one request — ccm will get a 401 on the cached token, then force-refresh
   - **Verification**: Check logs for `Copilot 401: force-refreshing token` followed
     by a successful response. See `docs/OAUTH_TESTING.md` for the full token
     expiry procedure.

### Developer Empathy Narrative

I open the README. There's a pre-built binary. I run the curl command, move it to PATH, run `ccm start`. The admin UI comes up at localhost:13456. I walk through the Copilot OAuth flow. Token gets cached. I point Claude Code at the proxy. My first few sessions work fine.

Then, mid-session after 3-5 turns, something breaks. Claude Code goes silent or falls back to a different provider. I check ccm logs — if I'm even running with verbose logging — and I see a `400 Bad Request` with no body from GitHub's API. I have no idea why it started failing mid-session. I restart ccm, the problem goes away. Next session: same thing.

After this fix: sessions run for 10+ turns without interruption. On startup I see `Copilot session established [session_id=abc123]` in logs — I know the fix is active. If a retry fires, I see `Copilot network retry [attempt=1]`. I can trust the proxy.
