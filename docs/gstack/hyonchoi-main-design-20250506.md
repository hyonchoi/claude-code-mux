## Problem Statement

NVIDIA NIM (NVIDIA Inference Microservices) is a containerized inference service that provides access to various LLMs including Claude, Llama, Mistral, and proprietary NVIDIA models. Currently, claude-code-mux doesn't support routing to NIM instances, limiting users who want to:
- Run LLMs locally via NIM containers
- Use NVIDIA's optimized inference stack
- Route to private/on-prem NVIDIA infrastructure

Adding NIM support enables users to seamlessly integrate their NVIDIA NIM deployments as another provider option in the multiplexer.

## What Makes This Cool

The NVIDIA NIM provider integration is elegant because:
1. **Zero new abstractions needed** — NIM uses OpenAI-compatible API format, so it fits perfectly into the existing `AnthropicCompatibleProvider` infrastructure
2. **Minimal implementation** — Can reuse the proven pattern from openrouter, z.ai, minimax, etc.
3. **Immediate value** — Users running NIM locally can immediately add it to their config and route Claude Code requests through it
4. **Flexible deployment** — Works with local NIM instances, self-hosted, or NVIDIA-hosted services

## Constraints

1. **NVIDIA NIM API compatibility** — Must support OpenAI-compatible Chat Completions API format (NIM implements this)
2. **Base URL requirement** — Users will provide their NIM instance URL (e.g., `http://localhost:8000` or cloud URL)
3. **Model discovery** — Users must manually specify which models their NIM instance supports
4. **No native token counting** — NIM doesn't provide tiktoken-compatible counting (will use OpenAI fallback or skip)
5. **Streaming support** — Must support SSE streaming (NIM does)

## Premises

1. **NVIDIA NIM API is OpenAI-compatible** — NIM implements OpenAI Chat Completions format with `/v1/chat/completions` endpoint
2. **Most users will self-host or use managed NIM services** — Configuration will be straightforward (base_url + api_key)
3. **Token counting is optional** — If NIM doesn't support it, we skip or estimate based on model
4. **Authentication is simple** — Either API key auth or no auth for local instances
5. **No special UI changes needed** — Standard provider config in TOML handles the setup

## Approaches Considered

### Approach A: Generic Anthropic-Compatible Provider (Recommended)
**Summary:** Treat NIM as another Anthropic-compatible provider, register it in the provider registry alongside openrouter/z.ai/minimax.

**Effort:** S (Small)  
**Risk:** Low  

**Pros:**
- ✅ Reuses `AnthropicCompatibleProvider` struct — zero new code needed
- ✅ Follows established pattern used by 5+ existing providers
- ✅ Users can configure in TOML: `provider_type = "anthropic"` with custom base_url
- ✅ Full support for streaming, authentication, model selection

**Cons:**
- ❌ Generic approach doesn't highlight NIM-specific features (batching, model management)
- ❌ Users must understand NIM's OpenAI compatibility themselves

**Reuses:** `AnthropicCompatibleProvider`, existing streaming infrastructure, auth patterns

---

### Approach B: Dedicated NIM Provider
**Summary:** Create a new `NimProvider` struct with NIM-specific optimizations (model introspection, batch API awareness).

**Effort:** M (Medium)  
**Risk:** Medium  

**Pros:**
- ✅ Could query NIM's `/v1/models` endpoint to auto-discover available models
- ✅ Could add NIM-specific features later (batching, priority inference)
- ✅ Better error messages for NIM-specific failures
- ✅ Could optimize for local instances vs. cloud deployments

**Cons:**
- ❌ Creates new code path that diverges from proven pattern
- ❌ Maintenance burden for NIM-specific logic
- ❌ Requires testing specific to NIM's API quirks
- ❌ Overkill for current use case (users just want routing)

---

### Approach C: Hybrid: NIM as a preset within AnthropicCompatibleProvider
**Summary:** Add NIM-specific factory method to `AnthropicCompatibleProvider` (like `zai_with_auth`, `minimax_with_auth`).

**Effort:** S (Small)  
**Risk:** Low  

**Pros:**
- ✅ Reuses core infrastructure, adds convenience factory method
- ✅ Could embed sensible NIM defaults (e.g., expected base_url pattern)
- ✅ Could document model discovery in the factory
- ✅ Leaves room for NIM-specific optimizations later

**Cons:**
- ❌ Slight code duplication if multiple NIM patterns exist
- ❌ Factory method adds optional complexity

---

## Recommended Approach

**Approach A (Generic Anthropic-Compatible)** because:

1. **NIM is already OpenAI-compatible** — the whole point of the `AnthropicCompatibleProvider` pattern
2. **Minimal implementation** — zero new code, just document how users configure NIM
3. **Proven pattern** — we've validated this approach with 5+ providers (z.ai, minimax, openrouter, etc.)
4. **Future-proof** — if NIM-specific features become critical, we can always add a dedicated provider or factory method later
5. **Ship speed** — documentation + config example = done in minutes

**Implementation path:**
1. Add NIM config example to `config/default.example.toml`
2. Document in README how to configure local/remote NIM instances
3. No code changes required (reuse existing infrastructure)
4. Optionally add `NimProvider::new()` factory method if community requests NIM-specific features

## Open Questions

1. **Token counting for NIM models** — Should we:
   - Fall back to OpenAI tokenizer estimates?
   - Return zero tokens (let client estimate)?
   - Wait for NIM to expose tiktoken endpoint?
   - **Current answer:** Use OpenAI fallback (safe, users get reasonable estimates)

2. **Which models to document?** — Which NIM models should we list as examples?
   - **Current answer:** Document that users can query `/v1/models` and pick any

3. **Local NIM setup docs** — Should README include Docker Compose example for running NIM locally?
   - **Current answer:** Document basic setup, link to NVIDIA's official guides

## Implementation Notes

### Code Changes (Minimal)

**No code changes required.** NIM will work immediately via existing infrastructure.

### Configuration Setup

Users will configure NIM like this:

```toml
[[providers]]
name = "nvidia-nim-local"
provider_type = "anthropic"  # Use Anthropic-compatible format
api_key = "your-nim-api-key"  # Leave empty if NIM is local with no auth
base_url = "http://localhost:8000/v1"  # Or your remote NIM endpoint
enabled = true
models = ["meta-llama-3.1-405b-instruct", "claude-3-5-sonnet-20241022"]  # Models available in your NIM

# Optionally route specific use cases to NIM
[router]
default = "nvidia-nim-local"  # Route all requests to NIM
# Or mix with other providers:
# default = "claude-opus"
# background = "nvidia-nim-local"  # Use NIM for background tasks
```

   - Local vs. remote setup considerations

2. **config/templates/nvidia-nim.toml** — Create template with:
   - Commented examples for local setup
   - Commented examples for remote/cloud setup
   - Notes on authentication

3. **CHANGELOG.md** — Document NIM support in next release

### Testing Approach

- **Unit test:** Verify that `AnthropicCompatibleProvider` can be configured with NIM parameters
- **Integration test:** Test against mock NIM server (using mockito or similar)
- **Manual test:** Test against real NVIDIA NIM instance if available

### Known Limitations

1. **Token counting** — NIM may not support Anthropic's token counting API; we'll use OpenAI tokenizer fallback
2. **Beta headers** — Some Anthropic-specific headers (like `anthropic-beta`) may not apply to NIM models; provider will ignore unsupported headers
3. **Model capabilities** — Tool use, vision, etc. depend on which models are in the NIM instance; users must verify

## Why This Matters

This change opens the door for organizations with NVIDIA infrastructure to use claude-code-mux as their unified LLM router, whether they're:
- Running LLMs on-prem via NIM containers
- Using NVIDIA's managed NIM services
- Building workflows that mix cloud (Anthropic/OpenAI) + local (NVIDIA) inference

The beauty is that the router architecture makes this a documentation problem, not an engineering problem. That's the kind of design win worth celebrating.
