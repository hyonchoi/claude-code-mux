## Problem Statement
Requests entering the relay with caller-provided OAuth credentials should preserve those credentials end-to-end, while still allowing router-driven model rewrites and upstream-error fallback within the same provider family.

## Constraints
- Never replace caller-provided passthrough auth with internally bootstrapped OAuth tokens.
- Allow model rewrite for routing, but preserve `original_model` for traceability.
- Fallback is triggered only on upstream availability errors (5xx/429/timeout/TLS).
- Block cross-provider fallback when passthrough auth would cross trust boundaries.
- Keep existing non-passthrough flows unchanged.

## Premises
1. Transparent relay behavior requires immutable caller auth context.
2. Model routing flexibility and auth immutability can coexist if tracked explicitly.
3. Same-provider-only fallback is the safest policy for passthrough-authenticated requests.

## Approaches Considered
### Approach A: Minimal Guardrail Patch
Summary: Add auth-preservation guards and same-provider fallback filters in existing flow.
Effort: M
Risk: Low
Pros:
- Smallest diff and quickest path to correct behavior.
- Low regression risk in critical request path.
Cons:
- Contracts stay partially implicit in current shapes.
Reuses:
- Existing router/provider/fallback plumbing.

### Approach B: Auth/Routing Envelope Split
Summary: Introduce explicit immutable AuthContext and mutable RoutingContext wrapper.
Effort: M
Risk: Medium
Pros:
- Strong long-term invariants and clearer testing boundaries.
- Better observability separation between auth and routing decisions.
Cons:
- Larger refactor surface for immediate goal.
Reuses:
- Existing handlers but with structural adaptation.

### Approach C: Passthrough Compatibility Mode
Summary: Add mode that leaves request untouched unless provider incompatibility appears.
Effort: S
Risk: Medium
Pros:
- Fastest trial path for incremental rollout.
- Useful as staging mode in mixed deployments.
Cons:
- Can accumulate branching complexity and hidden behavior.
Reuses:
- Current transform codepaths as staged adapters.

## Recommended Approach
Approach A. It meets the requested behavior with the least risk and fastest validation path, while preserving headroom to evolve into Approach B later if needed.

## Success Criteria
- Caller auth is preserved in passthrough paths.
- No internal OAuth bootstrap on passthrough requests.
- Model rewrite remains functional with `original_model` trace retained.
- Fallback triggers only on upstream availability categories.
- Cross-provider fallback is blocked for passthrough auth context.
- Normalized terminal error returned when fallback is exhausted.

## Open Questions
- Whether to introduce dedicated `AuthContext` type now or defer to follow-up refactor.
- Whether fallback retries should include configurable cap/backoff in this PR.
