## Problem Statement

GitHub Copilot's chat/completions API now requires a `model` field. Previously, ccm handled `model="auto"` by stripping the `model` key from the JSON body before forwarding — the API would then pick a default. That broke. The API now rejects requests without a model field. Need to resolve `"auto"` to a real Copilot model ID before forwarding.

## What Makes This Cool

The `/models` endpoint doesn't just fix "auto" — it gives ccm a live model catalog for free. Copilot goes from a special-case hack to a self-healing provider adapter. Zero manual model config. Stale-while-revalidate means Copilot API flakiness doesn't cascade to broken requests.

## Constraints

- Must match VS Code's Copilot extension behavior exactly (reference: `~/Work/vscode-copilot-chat`)
- Resolution lives inside `CopilotProvider` — router and other providers are unaware
- No startup blocking — lazy fetch on first "auto" request
- Must handle Copilot API flakiness (429 rate limits, transient failures)

## Premises

1. The Copilot API requires a model field — omit-field no longer works
2. "auto" should resolve to the `is_chat_fallback` model (matching VS Code's `copilot-base` family)
3. Resolution lives inside CopilotProvider — router/other providers unaware
4. Lazy fetch + in-memory cache with 10-min TTL (matching VS Code's 10-min refresh)
5. The `/models` response auto-populates the copilot provider's known models list

## Cross-Model Perspective

Codex cold read: the coolest version is not "fix auto" but a live Copilot capability registry inside CopilotProvider. `auto` becomes one consumer of a cached `/models` snapshot that also drives dynamic model list population and stale-while-revalidate behavior. The tell: "The /models response also auto-populates the copilot provider's known models list" — the excitement is removing operator burden, not just restoring broken behavior. Build `reqwest` + `tokio::sync::RwLock` cache with `{ fetched_at, fallback_model, discovered_models }`. Skip persistent disk cache, cross-provider discovery framework, background refresh.

## Approaches Considered

### Approach A: Minimal Viable — Auto-Resolution Only

Lazy fetch GET /models, cache the fallback model ID with 10-min TTL, substitute on "auto" requests. No stale-while-revalidate.

- Effort: S
- Risk: Low
- Pros: Smallest diff, matches VS Code core logic
- Cons: If /models fetch fails at TTL expiry, "auto" requests break; doesn't handle real-world 429 scenario

### Approach B: Self-Healing Registry — Auto + Stale-While-Revalidate

Same as A, but serve last-known-good model when TTL expires and refresh fetch fails. The `/models` snapshot becomes a living registry that degrades gracefully.

- Effort: S/M
- Risk: Low
- Pros: Resilient under Copilot API flakiness; matches VS Code's explicit 429 handling; ~15 extra lines over A
- Cons: Slightly more state; first-ever fetch failure still errors (correct behavior)

### Approach C: Config-Driven Override

Let users set `auto_model = "gpt-4o"` in copilot TOML config. Skip /models fetch if set.

- Effort: XS
- Risk: Low
- Pros: Zero network calls; works in air-gapped scenarios; escape hatch
- Cons: Doesn't eliminate config burden; diverges from VS Code reference; manual updates required

## Recommended Approach

**Approach B: Self-Healing Registry**

The VS Code reference code explicitly handles 429 on the /models endpoint — serving stale data on rate limit is a known real condition, not theoretical. ~15 extra lines buys resilience.

### Implementation Sketch

1. **New struct: `CopilotModelCache`** (inside `copilot.rs`)
   ```rust
   struct CopilotModelCache {
       fetched_at: Instant,
       fallback_model_id: String,
       discovered_models: Vec<CopilotModelInfo>,
   }

   struct CopilotModelInfo {
       id: String,
       name: String,
       family: String,
       capabilities_type: String,  // "chat", "completion", or "embeddings"
       is_chat_fallback: bool,
       is_chat_default: bool,
       model_picker_enabled: bool,
   }
   ```

2. **New fields on `CopilotProvider`**
   ```rust
   model_cache: Arc<RwLock<Option<CopilotModelCache>>>,
   ```
   Uses `tokio::sync::RwLock` for async-safe access.

3. **New method: `resolve_auto_model(&self) -> Result<String, ProviderError>`**
   - Fast path: cache exists and < 10 min old → return `fallback_model_id`
   - Expired path: attempt refresh GET `{base_url}/models`
     - Success → update cache, return new `fallback_model_id`
     - Failure (429, network error) → if stale cache exists, serve it + log warning; if no cache, error
   - No cache path: fetch GET `{base_url}/models`, parse, populate cache

4. **Request flow change** (in both `send_message` and `send_message_stream`)
   - Before constructing the JSON body, check `if request.model == "auto"`
   - If yes: `let resolved = self.resolve_auto_model().await?;` then set `request.model = resolved;`
   - The model field now contains the real ID (e.g., `gpt-4o`) when forwarded to Copilot
   - **Note on call graph**: `send_message_stream_with_url` is the shared internal method. Resolution should happen in the public `send_message` and `send_message_stream` trait methods (before they call into `send_message_stream_with_url`), because the resolution is specific to the "auto" model name and should not affect retry paths that already have a resolved model.

5. **GET /models request**
   - `resolve_auto_model()` calls `get_valid_copilot_token()` first (same flow as send methods), which returns the bearer token. The base URL is then extracted from that same bearer token via `parse_proxy_ep(&bearer)`.
   - URL: `format!("{}/models", parse_proxy_ep(&bearer))`
   - Headers: same `apply_copilot_headers` + `Authorization: Bearer {token}`
   - Response: JSON object `{ "data": [ ... ] }` — matches VS Code's `IModelAPIResponse[]`
   - Fallback selection (matching VS Code's `copilot-base` logic):
     ```rust
     // Priority: is_chat_fallback > is_chat_default > first chat model
     let fallback = data.iter()
         .find(|m| m.is_chat_fallback && m.capabilities_type == "chat")
         .or_else(|| data.iter().find(|m| m.is_chat_default && m.capabilities_type == "chat"))
         .or_else(|| data.iter().find(|m| m.capabilities_type == "chat"));
     ```

6. **Auto-populate models list**
   - After successful fetch, update `self.models` with discovered chat model IDs
   - This means `supports_model()` will return true for any model the Copilot API actually exposes
   - No TOML editing needed for new Copilot models
   - **Scope note**: This is a convenience feature bundled with the /models fetch. If it introduces issues (e.g., preview/deprecated models appearing that operators don't want), it can be split into a follow-up change with a filter allowlist. For v1, all discovered chat models are accepted.

### Edge Cases

- **First-ever fetch fails**: Return error — no stale data to serve. Correct behavior.
- **429 on refresh**: Serve stale cache. Log warning. VS Code does exactly this.
- **Token not yet available**: `get_valid_copilot_token()` handles this. The /models fetch happens after token acquisition.
- **Concurrent cold-start requests**: Multiple "auto" requests arriving when cache is empty could trigger multiple /models fetches. Use a separate `model_fetch_lock: Arc<Mutex<()>>` (distinct from `refresh_lock` which guards token refresh) to deduplicate — only the first caller fetches, others wait and read the populated cache. The lock is held only during the fetch; subsequent requests hit the cache without contending.
- **No `is_chat_fallback` model in response**: Fall back to `is_chat_default`, then first chat model in list. Log warning.
- **Empty `data` array**: Same code path as "no fallback model found" — the fallback chain returns `None`, resulting in an error. Correct behavior.
- **Model="auto" but request is not for copilot provider**: Router already routes by provider — copilot only sees requests destined for it.

## Success Criteria

- `model="auto"` requests to Copilot succeed (200 response with real content)
- The resolved model ID matches what VS Code's `copilot-base` family resolves to
- Cache refreshes every 10 minutes
- Stale cache served on refresh failure (429, network error)
- First "auto" request after server start triggers exactly one /models fetch
- `supports_model()` returns true for models discovered via /models
- All existing copilot tests still pass
- New tests: cache hit, cache miss + fetch, TTL expiry, stale-while-revalidate, no fallback model found
