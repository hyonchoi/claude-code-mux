## Overview

This test plan covers the passthrough auth preservation feature for incoming Claude Code requests. The feature preserves caller OAuth context end-to-end instead of replacing it with internally managed sessions.

## Affected Endpoints

- `POST /v1/chat/completions` (OpenAI-compatible relay entry point)
- Provider layer: `send_message()` implementations for all providers

## Key Interactions to Verify

### 1. Auth Context Preservation
- Incoming `Authorization: Bearer <user-token>` header is extracted and preserved
- Incoming `X-API-Key: <key>` header is extracted and preserved
- Non-passthrough requests continue to use provider config credentials
- Token source is deterministic: incoming auth > config auth

### 2. Same-Provider Fallback Boundary
- When passthrough auth fails with upstream error, fallback is restricted to same-provider targets only
- Cross-provider fallback is blocked for passthrough-authenticated requests
- Fallback is still allowed for non-passthrough (config-based auth) requests
- Provider origin is correctly extracted from auth header

### 3. Error Categorization & Fallback Triggering
- HTTP 5xx errors trigger fallback attempt (same-provider only)
- HTTP 429 (rate limit) errors trigger fallback
- Connection timeouts trigger fallback
- TLS/cert validation failures trigger fallback
- HTTP 401/403 (auth rejection) do NOT trigger fallback (terminal error)
- Request-shape validation errors do NOT trigger fallback

### 4. Fallback Exhaustion & Error Response
- All fallback providers attempted in order before returning error
- Error response is normalized to OpenAI format (not raw upstream error)
- Error response includes trace fields: original_model, fallback_target, upstream_error_class
- Sensitive data (tokens, credentials) is masked in error responses

### 5. Request Mutation & Audit Trail
- Original model parameter is preserved and included in response (for transparency)
- Model rewrite by router/fallback logic is logged but doesn't affect original_model field
- Request state is not corrupted across fallback attempts

### 6. Structured Logging & Observability
- Request entry logs include: `auth_preserved`, `passthrough_mode`, `provider_origin`
- Fallback attempt logs include: `fallback_triggered`, `upstream_error_class`, `fallback_target`
- Audit trail is structured (JSON/KV format) for post-incident debugging

## Critical Tests (Must Pass Before Shipping)

### Test 1: Passthrough OAuth Token Preserved
**What to test:** Incoming OAuth token flows through to provider unchanged
**Where:** POST /v1/chat/completions
**Setup:**
- Request with `Authorization: Bearer user_token_xyz`
- Model that maps to multiple providers
- First provider in mapping is available and responsive

**Steps:**
1. Send request with incoming OAuth token
2. First provider should receive request with `Authorization: Bearer user_token_xyz`
3. Verify provider does NOT receive config-based token

**Expected:** Provider receives exact incoming token, not internal OAuth

---

### Test 2: Passthrough API-Key Preserved
**What to test:** Incoming API key is preserved
**Where:** POST /v1/chat/completions
**Setup:**
- Request with `X-API-Key: client_key_abc`
- Model mapped to OpenAI provider

**Steps:**
1. Send request with incoming API key
2. Provider should receive `X-API-Key: client_key_abc`

**Expected:** Provider gets client's API key, not config key

---

### Test 3: Malformed Auth Header Rejected
**What to test:** Invalid auth format is caught early
**Where:** POST /v1/chat/completions
**Setup:**
- Request with `Authorization: InvalidFormat xyz` (not Bearer or ApiKey)
- Valid model

**Steps:**
1. Send malformed auth header
2. Handler should validate and reject

**Expected:** HTTP 400, error message "Invalid Authorization header format"

---

### Test 4: Same-Provider Fallback Allowed
**What to test:** Fallback works within same provider family
**Where:** POST /v1/chat/completions
**Setup:**
- Request with `Authorization: Bearer anthropic_token`
- First provider (Anthropic) configured to fail with HTTP 500
- Second provider (Anthropic) configured to succeed
- Both providers in config

**Steps:**
1. Send passthrough request to claude-opus
2. First provider fails with 500
3. Fallback should attempt second Anthropic provider
4. Request should succeed with second provider

**Expected:** Request routed to second provider, not attempted with different provider family

---

### Test 5: Cross-Provider Fallback Blocked for Passthrough
**What to test:** Fallback does NOT jump to different provider family
**Where:** POST /v1/chat/completions
**Setup:**
- Request with `Authorization: Bearer anthropic_token` (Anthropic origin)
- First provider is Anthropic (fails with 500)
- Second provider is OpenAI (available)
- Both in config

**Steps:**
1. Send passthrough request
2. Anthropic provider fails with 500
3. OpenAI provider should NOT be attempted

**Expected:** Fallback skips OpenAI, returns terminal error (not attempted)

---

### Test 6: HTTP 5xx Triggers Fallback
**What to test:** 5xx errors trigger fallback retry
**Where:** POST /v1/chat/completions
**Setup:**
- Provider configured to return HTTP 500
- Second provider available

**Steps:**
1. Send request
2. First provider returns 500
3. Check logs for fallback_triggered event

**Expected:** Fallback_triggered=true, second provider attempted

---

### Test 7: HTTP 401 Does NOT Trigger Fallback
**What to test:** Auth rejection is terminal (don't fallback)
**Where:** POST /v1/chat/completions
**Setup:**
- Passthrough auth from OpenAI
- Provider returns HTTP 401 (invalid token)

**Steps:**
1. Send request with invalid token
2. Provider returns 401
3. Check logs for fallback_triggered

**Expected:** Fallback_triggered=false, error returned immediately (not retried)

---

### Test 8: Fallback Exhaustion Returns Normalized Error
**What to test:** All fallbacks failed → return standard error
**Where:** POST /v1/chat/completions
**Setup:**
- 3 providers in config, all fail with 500
- Passthrough request

**Steps:**
1. Send request
2. All 3 providers fail with 500
3. Check response format

**Expected:** Response is normalized OpenAI format, includes original_model and error trace

## Edge Cases to Cover

- Empty Authorization header → passthrough mode disabled (use config)
- Token with no claims → treat as opaque string, use as-is
- Provider origin extraction fails → log warning, proceed without same-provider boundary
- Forced provider header + same-provider constraint → respect constraint (don't override across families)
- Token refresh not triggered for passthrough auth → verify assertion

---

## Success Criteria

✓ All 8 critical tests pass
✓ All 2 medium tests pass
✓ Edge cases handled gracefully (errors logged, no crashes)
✓ Structured logging contains all required fields
✓ No passthrough tokens are logged or exposed in error responses
✓ Backward compatibility: non-passthrough requests work unchanged
