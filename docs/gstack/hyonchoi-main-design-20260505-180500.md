## Problem Statement
Incoming Claude Code requests should preserve caller OAuth context instead of being replaced by internally managed OAuth sessions. The relay should stay transparent by default, allow model replacement when routing requires it, and perform fallback substitution only when upstream endpoint/provider errors occur.

## What Makes This Cool
The core delight is invisible reliability: clients keep sending familiar Claude-style requests and get seamless behavior without re-auth flows, manual endpoint rewrites, or brittle client-side recovery logic.

## Constraints
- Preserve incoming auth context end-to-end for passthrough requests.
- Model parameter rewriting is allowed, but auth context must remain authoritative.
- Fallback routing should be upstream-error-triggered, not always-on mutation.
- Minimize breakage in existing routing priority and provider plumbing.
- Keep compatibility with current OpenAI/Anthropic transform paths.

### Auth Context Definition
- Immutable fields: `Authorization`, `X-API-Key` (if present), and provider-auth metadata that originates from caller request context.
- Mutable fields: `model`, target provider selection, and endpoint URL used for fallback routing.

### Upstream Error Taxonomy (Fallback Triggers)
- Trigger fallback routing on: upstream HTTP 5xx, HTTP 429, connection timeout, and TLS/connectivity failure.
- Do not trigger fallback routing on: upstream auth rejection (401/403) for cross-provider paths, and request-shape validation errors caused by client payload mismatch.

## Premises
1. Transparent passthrough means preserving incoming OAuth/bearer context as the source of truth.
2. Routing may replace target model/provider while retaining original auth context.
3. Fallback routing should happen only on upstream error conditions.

## Approaches Considered
### Approach A: Minimal Relay Guardrail
Summary: Add guardrails that freeze incoming auth context, allow model parameter rewriting through existing router/fallback logic, and only invoke fallback routing on upstream error.
Effort: M
Risk: Low
Pros:
- Fastest route to the requested behavior.
- Smallest diff in critical proxy paths.
- Preserves current architecture and operational familiarity.
Cons:
- Contracts remain implicit in code rather than a formal envelope.
- Future extensibility may require follow-up refactor.
Reuses:
- `src/router/mod.rs`
- `src/providers/openai.rs`
- Existing provider registry and fallback flow

### Approach B: Split Auth-Context + Routing Envelope
Summary: Introduce immutable auth_context plus mutable routing_context to enforce explicit separation of security and routing decisions.
Effort: M
Risk: Medium
Pros:
- Clean long-term architecture with strong invariants.
- Easier testability and observability for auth vs routing behavior.
Cons:
- Larger rollout with greater regression surface now.
- Slower time to user-visible fix.
Reuses:
- Existing request transform layers, but with structural refactor

### Approach C: Passthrough-First Compatibility Mode
Summary: Add a compatibility mode that keeps request untouched unless provider incompatibility appears, then applies staged minimal transforms.
Effort: S
Risk: Medium
Pros:
- Minimally invasive launch path.
- Useful for experimentation in mixed provider deployments.
Cons:
- Can become hard to reason about under cascading failures.
- Risk of hidden branching complexity over time.
Reuses:
- Existing transformation codepaths as staged adapters

## Recommended Approach
Choose Approach A (Minimal Relay Guardrail).

Rationale:
- Matches the explicit requirement: keep incoming OAuth context and avoid internal OAuth replacement.
- Delivers transparent passthrough quickly with low implementation risk.
- Supports model replacement and error-based fallback without large architectural churn.

## Auth Preservation During Provider Fallback — Decision
Current contradiction addressed: caller OAuth from one provider cannot be replayed safely against a different provider.

Chosen policy:
- Same-provider fallback only for passthrough-authenticated requests.
- Cross-provider fallback is disabled for passthrough-authenticated requests.
- No internal OAuth substitution is allowed in these passthrough paths.

Same-provider definition:
- Same OAuth authority domain and auth trust boundary (for example, Anthropic-authenticated requests may only fallback to Anthropic provider targets).
- Endpoint URL/path changes within that trust boundary are allowed.

Rationale:
- Preserves transparent caller-auth semantics.
- Avoids hidden auth translation behavior.
- Keeps failure behavior predictable and debuggable.

## Resolved Questions
- Immutable passthrough fields: `Authorization`, `X-API-Key`, and provider-auth metadata from caller context.
- Mutable fields: `model`, provider target within same provider family, and endpoint URL.
- Fallback metadata: preserve original model as trace field for debugging/audit.
- Internal OAuth override location review: audit starts in relay entry and provider auth-header assembly paths before implementation.
- Provider-specific auth headers: no new handling in this scope beyond existing bearer/API-key passthrough behavior.

## Passthrough Example
- Request IN: caller sends `Authorization: Bearer <user-token>`, `model: claude-4-5-sonnet`, and passthrough request payload.
- Relay behavior: preserve auth headers exactly, allow model parameter rewriting by router policy, then send upstream.
- On upstream error trigger: perform fallback routing only to same-provider backup model/endpoint within the same auth trust boundary.
- If same-provider fallback is unavailable or fails, return terminal normalized upstream error to caller.

## Success Criteria
- Incoming OAuth/bearer context is preserved end-to-end in passthrough flow.
- No internal OAuth session bootstrap occurs for these incoming requests.
- Model parameter rewriting works when router/fallback policy requires it.
- Fallback routing executes only on upstream error conditions and only within same-provider fallback for passthrough-authenticated requests.
- Existing non-passthrough request flows continue working unchanged.
- Structured logs include: `auth_preserved`, `model_rewritten`, `fallback_triggered`, `upstream_error_class`, `original_model`, `fallback_target`.
- Error propagation contract: if same-provider fallback fails, return terminal upstream error with normalized status/body contract and no cross-provider auth mutation.
- Minimum integration coverage: auth preservation (3), model rewrite with preserved auth (2), fallback routing across error classes (5), backward-compat non-passthrough checks (2).
